# PRD：Auto Organization — 标签聚类治理 / 相似笔记归夹 / 连续笔记合并

Status: ready-for-agent
Version: v0.1
Created: 2026-09-12
Parent feature: usable-product-iteration（A1 自动打标闭环是其上游；S1/S2 的 Semantic Diff 与锚定体系是合并能力的上游）

## Problem Statement

A1 把「识别→自动打标」闭环跑通后，标签体系失控：对真实文档库实测（2026-09-12，43 篇文档）**词表已膨胀到 243 个标签、平均每文档 6.7 个，其中 212 个（87%）只被一篇文档使用**——自动打标为每页手稿发明一套细粒度新词（`基圆半径`、`滚子半径`、`sram`、`dram` 各自独立），词表优先语义只拦得住字面变体，拦不住语义近义。标签视图只能逐个 `prompt()` 重命名/合并，243 个标签靠手工治理不现实。

同时笔记组织仍然平铺：同一主题的笔记散落（控制理论、概率论、机械原理各据一方却没有聚拢机制——`notes/classify.py` 的分类能力只在导出 Obsidian 时才运行）；PDF 逐页入库把一本讲义拆成 N 份独立文档（共享 `source_job_id` 的连续页），重拍/补拍的手稿与原件高度重叠——这些**显著连续的笔记应当合并**而不是并列堆积。

## Solution

在文档库之上加**自动整理层**，三条能力共用一套纪律：**LLM 只提议、确定性函数落地、人确认后执行**（沿 S2 pHash 候选与 R1/A1 的 dry-run 预算纪律）：

1. **标签语义聚类治理**（issue 01）：LLM 审计整个词表 → 产出机器可校验的「治理方案」（同义合并对 + 主题分组）→ 批量复核确认后确定性应用（复用 `merge_vocabulary_tags`），词表 schema 升 v2 持久化主题分组，标签视图分组渲染。
2. **相似笔记自动归类到集合（文件夹）**（issue 02）：确定性内容相似度生成候选对（零 LLM）→ LLM 对全库做主题归类，产出复用 `ClassificationScheme` 校验的方案 → 确认后写入集合归属（auto 来源与手工 `manual_collections` 可区分）；集合 slug 即 Obsidian 导出文件夹键，归夹结果导出即变现。
3. **显著连续笔记合并**（issue 03）：连续对检测（同 `source_job_id` 页序相邻 = 强信号；pHash 候选 + 尾首块重叠 = 辅信号）→ IR 块级合并执行器（拼接 + 重叠块去重，消费 S1 DiffReport）→ 原稿软归档可恢复。显著档批量执行、疑似档逐条确认，**绝不静默合并**。

## User Stories

1. 作为用户，我想一键审计标签词表并得到「哪些该合并、按什么主题分组」的方案，以便 243 个标签收敛到可治理的规模
2. 作为用户，我想逐条或批量接受/拒绝治理建议，以便纠错成本远低于手工整理
3. 作为用户，我想标签视图按主题分组展示，以便浏览时看到结构而不是平铺的 243 个词
4. 作为用户，我想相似主题的笔记自动聚拢到同一个集合（文件夹），以便按课程/科目复习时同类笔记都在一处
5. 作为用户，我想自动归类与手工归类可区分、可互相转化，以便始终知道哪些是机器放的
6. 作为用户，我想同一 PDF 的连续页、内容首尾衔接的补拍手稿被识别为「连续」并合并成一篇，以便讲义不再碎成 N 份文档
7. 作为用户，我想合并是可逆的（原稿不丢、可恢复），以便放心让系统动手
8. 作为用户，我想所有自动整理先 dry-run 报告规模与预估调用数，以便控制 LLM 预算

## Implementation Decisions

- **无 embedding**：沿仓库刻意决定（`unifiedsearch.py`/`pdfsearch.py` 明示）。语义聚类走 LLM 提议；候选生成走确定性算法（shingle Jaccard / 页序 / pHash / S1 块匹配），纯函数可快照
- **LLM 提议 → schema 校验 → 确定性应用**：治理/归类方案均为 pydantic 可校验结构，非法输出（引用不存在标签、合并成环、超上限）直接拒绝；录制 golden fixture，CI 无 live 调用（沿 A1/knowledge-workspace issue 02 口径）
- **确认后执行，provenance 可区分**：自动写入走 `collections`（auto）与手工 `manual_collections` 分流；标签 merge/rename 复用既有治理函数；合并操作在版本链标注 `merge` 来源（沿 R1 repair 字段约定）
- **合并可逆**：原稿软归档标记 `merged_into`，不删除；Library 默认列表排除归档稿但保留直达链接；恢复 = 清除标记
- **宜粗不宜细**：主题分组/集合归类的一级类目 ≤ 8（沿 `notes/classify.py` DEFAULT_MAX_TOPICS 口径）；首版一个标签至多属于一个主题组（取舍记录在案，多归属留 follow-up）
- **失败不阻塞**：整理任务全部独立于解析管线；LLM 失败只留 warning + 遥测，不产生影响主功能的副作用

## Testing Decisions

- **纯函数 seam（最高价值）**：相似度候选、治理方案应用、IR 合并执行器均为纯函数 → fixture 快照/表驱动断言
- **LLM seam**：治理方案与归类方案用录制 golden fixture（含"合法方案""非法引用被拒""成环被拒"三类），CI 不 live 调用
- **API/UI seam**：store stub 集成测试确认写入路径与 provenance 分流；离线 DOM 断言复核队列行为
- **验收基线**：真实库 43 篇 / 243 标签的整理结果记录在 handoff（合并对数、分组数、归夹分布、合并文档数与预算消耗）
